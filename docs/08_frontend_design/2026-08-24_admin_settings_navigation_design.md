# Admin UI `설정` 대분류 신설 — 내비게이션/화면 설계 문서

> **상태**: 📝 설계 전용(이번 문서 작성 시점 기준 구현 미착수)
> **목적**: 이전 read-only 조사("백엔드에는 설정/운영 조치 API가 있지만 Admin UI에는
> 대응 화면이 없는 항목" 조사)를 바탕으로, 좌측 내비게이션에 `설정` 대분류를 신설하고
> 그 하위 메뉴 구성/화면 레이아웃/단계별 구현 순서를 설계한다.
> 이번 문서는 정보 구조·레이아웃·상태 표현 설계까지만 다루며, 실제 컴포넌트 구현은
> 후속 작업이다(이번 턴은 Admin UI 코드를 수정하지 않았다).
>
> **개정**: 최초안에는 `설정` 하위에 `진단 스냅샷` 메뉴가 포함돼 있었으나, 이번 개정에서
> **제외**했다. `guardrail-evaluations`/`risk-limit-snapshots`/`signal-feature-snapshots`는
> "설정값"이 아니라 조회 전용 진단 데이터라 `설정` 대분류에 넣는 것 자체가 성격에 맞지 않고,
> 각각 더 어울리는 기존 화면이 있어(§3.3) 별도 "후속 관측 화면 후보"로 분리했다. 또한 좌측
> 내비 메뉴 수가 늘어나는 문제에 대한 검토(§4)를 추가했다.

## 1. 배경

### 1.1 왜 `설정` 대분류가 필요한가

`admin_ui/AGENTS.md`는 Admin UI를 "운영자가 백엔드 상태를 오해하지 않게 만드는 read/inspect
중심 화면"으로 규정한다. 실제로 현재 Admin UI 전체를 뒤져 보면(`client.ts`의 POST/PUT/DELETE
호출은 실시간 시세 구독/해지 단 1쌍뿐), **사실상 100% 조회 전용 콘솔**이다. 그런데 백엔드에는
이미 아래와 같은, 명백히 "운영자가 조정해야 하는" API가 존재한다.

- `POST /config-versions/risk/max-single-position-pct` — 리스크 한도(단일 포지션 최대 비중) 조정
- `POST /config-versions/execution-fee-tax` — 수수료/세금 정책 등록(dry-run 지원)
- `GET /config-versions/execution-fee-tax/active`, `/at` — 현재/특정 시점 정책 조회
- `PUT /orders/{order_request_id}/status` — `RECONCILE_REQUIRED` 주문 수동 확정(admin 전용 운영 조치)

지금은 이 값을 바꾸거나 확인하려면 운영 서버에 SSH로 접속해 CLI 스크립트
(`scripts/publish_max_single_position_pct.py`, `scripts/publish_fee_tax_policy.py`)를 실행하거나,
`PUT /orders/{id}/status`를 curl로 직접 호출해야 한다. 이 방식은:

- 화면 가이드 없이 evidence(`source`, `checked_at`) 같은 필수 필드를 손으로 맞춰야 해서 실수하기 쉽고,
- "지금 값이 얼마인지" 확인할 방법이 화면에 전혀 없어(특히 `max_single_position_pct`는 조회 API 자체가 없음)
  운영자가 상태를 오해하기 쉬우며,
- 감사 추적(누가 언제 무엇을 바꿨는지)을 화면에서 확인할 수 없다.

`설정` 대분류는 이 API들을 "예쁘게 꾸민 설정 콘솔"로 만드는 게 목적이 아니라, **이미 존재하는
쓰기 능력을 운영자가 오해 없이, 안전하게 쓰도록 최소한의 가드레일을 씌우는 것**이 목적이다.

### 1.2 지금 화면이 비어 있는 이유를 오해하지 않기

이전 조사에서 구분했듯, "화면이 없는 이유"는 두 가지로 나뉜다.

1. **API는 있는데 화면이 없음** — 이번 문서의 대상(`max-single-position-pct`, `execution-fee-tax`,
   `PUT /orders/{id}/status`).
2. **API 자체가 아직 없음** — `daily_loss_limit_pct`, `weekly_loss_limit_pct`, `max_drawdown_pct`,
   `kill_switch.*`, `execution.max_slippage_bps` 등. `config_version_admin.py`가 "이번 버전은
   `risk.max_single_position_pct` 단일 키만"이라고 명시적으로 범위를 좁혀 놓았다. 이건 화면 설계로
   해결할 수 없는 **백엔드 선행 과제**이므로, 이번 설계에서는 "준비 중" 상태로만 다룬다.

여기에 하나를 더 구분해야 한다.

3. **API도 있고 화면도 필요하지만, "설정"이 아니라 "관측/진단"인 것** — `guardrail-evaluations`,
   `risk-limit-snapshots`, `signal-feature-snapshots`. 값을 바꾸는 게 아니라 "왜 이 결정/주문이
   이렇게 됐는지"를 보여주는 조회 전용 데이터라, `설정` 대분류에 넣으면 운영자가 "이걸 여기서
   바꿀 수 있나?"라고 오해할 수 있다. 이번 개정에서 `설정`에서 완전히 빼고 §3.3에서 별도로 다룬다.

## 2. 설계 원칙

1. **읽기 전용 우선** — 모든 새 설정 화면은 "현재값을 정확히 보여준다"를 먼저 완성하고, 그 다음에만
   수정 기능을 붙인다. 현재값을 보여줄 API가 없으면(`max_single_position_pct`) 수정 UI를 먼저
   만들지 않는다.
2. **현재값 없는 수정 금지** — "무엇을 얼마에서 얼마로 바꾸는지" 화면에 diff로 보여줄 수 없는 값은
   발행 버튼을 노출하지 않는다("백엔드 준비 중" 상태로 대체).
3. **dry-run → 확인 → 실제 발행 3단계 분리** — `execution.fee_tax`처럼 dry-run API가 있는 값은
   이 흐름을 그대로 화면에 반영한다. dry-run 없이 바로 발행 API가 있는 값(`max_single_position_pct`)도
   프론트에서 "미리보기(변경 전/후 diff) → 확인 모달 → 실제 제출" 3단계를 강제해, 백엔드에 dry-run이
   없다는 이유로 사용자 경험까지 위험하게 만들지 않는다.
4. **401/403/400/500/empty/stale를 절대 뭉개지 않는다** —
   - `401`(토큰 만료) → 기존 전역 로그아웃 처리(`AuthContext`의 `onUnauthorized`)와 동일하게 처리.
   - `403`(권한 부족) → "인증은 됐지만 이 조작을 할 권한이 없음"을 별도 문구로 표시한다.
   - `400`(검증 실패) → 백엔드 `build_http_exception`이 이미 `field`/`expected`/`received`/`next_action`을
     구조화해서 내려준다([`ai_friendly_error_message_contract.md`](../80_harness_engineering/ai_friendly_error_message_contract.md)
     계약) — 이 필드들을 그대로 화면에 노출해 "왜 실패했는지"를 운영자가 바로 알게 한다.
   - `500`/네트워크 오류 → "저장 실패, 다시 시도" 배너. **절대 성공처럼 보이지 않게** 한다.
   - `empty`(아직 발행 이력 없음, 예: `execution-fee-tax/active`가 `config_version_id: null` 반환) →
     오류가 아니라 "아직 등록된 정책 없음"으로 표시(백엔드 주석이 이미 "오류가 아니다"라고 명시).
   - `stale` — 화면을 연 시점의 값과 실제 발행 시점의 값이 다를 수 있으므로(다른 운영자가 먼저
     바꿨을 가능성), 발행 직전에 현재값을 한 번 더 조회해 화면에 남아있던 값과 다르면 경고하고
     제출을 막는다.
5. **"값을 바꿨다"는 착시 금지** — 발행 API 호출 후 응답을 받기 전까지는 카드에 새 값을 절대
   먼저 반영하지 않는다(optimistic update 금지). 성공 응답을 받은 뒤 그 응답의 값으로만 갱신한다.
6. **백엔드 enum/schema/RBAC와 어긋나는 해석 금지** — `environment`는 `'paper' | 'live'`만
   허용(`Environment` enum에 `'real'`이 있어도 DB 제약상 거부됨, `config_versions.py:116-121`
   주석 참고) — 프론트 select 옵션도 이 2개만 노출한다.

## 3. 좌측 내비 제안

### 3.1 기존 구조와의 관계

현재 `navSections`(`Layout.tsx:54-86`)에는 이미 **"예약됨"** 섹션 아래 `disabled: true`인
"관리"(`ShieldCheck` 아이콘) 항목이 존재한다. 이름과 아이콘이 이번에 만들 `설정` 대분류와
개념적으로 겹친다. **"예약됨 > 관리"를 그대로 두고 별도로 "설정"을 새로 만들면 운영자 입장에서
두 메뉴가 뭐가 다른지 헷갈린다.** 따라서 이번 설계는 **"예약됨 > 관리" 항목을 제거(또는 이름을
"설정"으로 바꿔 재사용)하고, 그 자리에 활성화된 "설정" 섹션을 넣는 안**을 제안한다.

### 3.2 최종안

```
운영 모니터링
├── 운영 대시보드
├── 유니버스 선정
├── 주문 추적
├── 운영 경고
└── 정합성 점검

기본 운영
├── 현재가
├── 주문내역
├── 체결내역
├── 계좌
│   ├── 계좌잔고
│   └── 실현손익
├── 의사결정
└── 에이전트 실행

설정                                   ← 신설
├── 권한 확인                          ← §8 1단계 완료 후 활성화
├── 수수료·세금 정책                    ← §8 3~5단계
└── 리스크 한도                        ← 백엔드 선행(§8 6단계) 전까지 "준비 중"

예약됨
├── 브로커                             (비활성 유지)
└── 시스템                             (비활성 유지)
```

이번 개정에서 `설정`은 **3개 메뉴로 확정**한다. 최초안에 있던 `진단 스냅샷`은 제외했다 —
이유와 각 API의 대안 배치는 §3.3을 참고한다.

`정합성 점검`은 **`설정`으로 옮기지 않는다.** `PUT /orders/{id}/status`는 이번 조사 결론(§0)대로
"설정값"이 아니라 특정 주문에 대한 1회성 운영 조치이므로, 기존 "운영 모니터링 > 정합성 점검"
화면 안의 행 단위 액션으로 붙이는 것이 자연스럽다(§7.4).

### 3.3 후속 관측/진단 화면 후보 (설정 메뉴 아님)

`guardrail-evaluations`, `risk-limit-snapshots`, `signal-feature-snapshots`는 값을 조회만 하는
진단/스냅샷 API로, "설정"이 아니다. 새 대분류를 만들 만큼 우선순위가 높지도 않아, 각각 이미
존재하는 관련 화면의 상세 패널에 흡수하는 쪽을 1차 방향으로 제안한다. **이번 `설정` 대분류
작업 범위에는 포함하지 않고, 별도 후속 작업으로 분리한다.**

| API | 제공 데이터 | 붙일 위치(제안) | 근거 |
|---|---|---|---|
| `GET /guardrail-evaluations*` | 가드레일 규칙 평가 결과(`blocking_rule_codes`/`warning_rule_codes`), `decision_context_id`/`order_request_id`로 조회 가능 | `의사결정`(`DecisionsView.tsx`) 상세 패널, 또는 `주문내역`(`OrdersView.tsx`) 상세의 "차단 근거" | 이미 `decision_context_id`/`order_request_id` 단위로 조회하는 API라, 그 두 화면의 상세 조회 흐름에 자연스럽게 끼워 넣을 수 있다 — 독립 화면을 새로 만들면 오히려 "왜 막혔는지"를 보려고 화면을 왕복해야 해서 더 불편하다 |
| `GET /risk-limit-snapshots*` | 계좌별 시점 스냅샷(NAV, 노출도, VaR, drawdown_state, kill_switch_active 등) | `운영 경고`(`OperationsAlertsView.tsx`)의 근거 카드 또는 `계좌`(`AccountsView.tsx`)/`의사결정` 상세의 리스크 근거 카드 | 계좌 단위 시계열 데이터라 `계좌` 화면과 궁합이 가장 좋고, `kill_switch_active`/`drawdown_state`처럼 경고성 값은 `운영 경고`에도 근거로 붙일 수 있다 — 두 화면 중 어디에 먼저 붙일지는 실제 구현 시점에 운영자 실사용 패턴을 보고 결정 |
| `GET /signal-feature-snapshots*` | 종목/timeframe별 신호 피처 스냅샷 | `의사결정`(`DecisionsView.tsx`) 상세의 "신호 근거" | 의사결정이 어떤 신호값을 근거로 내려졌는지 보여주는 데이터라, 결정 상세 화면에 직접 붙는 것이 가장 직관적이다 |

이 표는 "화면화 필요성과 대략의 위치"만 정리한 것이고, 각 화면에 실제로 붙일지/얼마나 자세히
보여줄지는 해당 화면(`DecisionsView`/`OrdersView`/`AccountsView`/`OperationsAlertsView`)을 다시
설계 검토할 때 별도로 판단한다(§10 미확인 사항).

## 4. 좌측 내비 세로 길이 증가 문제 검토

### 4.1 현황

지금도 좌측 내비는 "운영 모니터링"(5) + "기본 운영"(6, 계좌 하위 2개 포함) + "예약됨"(3, 비활성)
=  14개 행이다. 여기에 `설정` 3개를 더하면 17개 행(그룹 헤더 3개 포함)이 된다. 화면이 늘어날
때마다 이런 식으로 계속 추가되면, 특히 세로 해상도가 작은 노트북/태블릿에서는 사이드바 자체가
스크롤돼야 하거나 하단 로그아웃 버튼이 화면 밖으로 밀려나는 문제가 생길 수 있다.

### 4.2 검토한 대안

| 대안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 1. 그룹 접기/펼치기 | `운영 모니터링`/`기본 운영`/`설정` 등 그룹 헤더를 클릭하면 하위 항목을 접고 펼침 | 화면 하나에 필요한 그룹만 펼쳐두면 세로 길이를 크게 줄일 수 있음. 그룹 수가 계속 늘어나도 확장 가능한 구조 | 상태(어떤 그룹이 펼쳐져 있는지)를 어딘가 저장해야 함(세션/로컬스토리지) — 안 그러면 새로고침마다 다 펼쳐진 채로 시작해 효과가 없음. 운영자가 자주 쓰는 화면이 접힌 그룹 안에 있으면 클릭이 한 번 더 필요해짐 |
| 2. 사용 빈도 낮은 항목을 하위 화면 탭으로 이동 | 예: `설정` 안의 세부 메뉴를 사이드바가 아니라 `설정` 진입 화면 안의 좌측 서브탭/상단탭으로 배치 | 사이드바 자체의 행 수는 그룹당 1개로 고정됨 | Admin UI 공용 컴포넌트에 탭 프리미티브가 없음(§7.5와 동일한 문제) — 새 컴포넌트가 필요하고, "설정 메뉴가 사이드바에 없다"는 사실 자체가 신규 기능 존재를 덜 눈에 띄게 만들 수 있음 |
| 3. `예약됨` 섹션 제거/축소 | 아직 아무 기능도 없는 "브로커"/"시스템"(그리고 이번에 없앨 "관리") 3개 행을 통째로 없애거나, 그룹 헤더 없이 맨 아래 흐리게 1줄로만 표시 | 즉시 3행(그룹 헤더 포함 4행) 감소 — 별도 컴포넌트 없이 가장 빠르게 적용 가능 | "앞으로 만들 화면들"이라는 로드맵 신호가 사라짐. 다만 이건 운영자에게 큰 정보 가치가 없는 신호라 잃어도 되는 손실로 보임 |
| 4. 데스크톱 사이드바에 내부 스크롤 적용, 모바일은 현재 패턴 유지 | `<aside>`에 `overflow-y-auto` + 하단 로그아웃 버튼만 `sticky bottom-0`으로 고정 | 구현이 가장 작음(CSS 한두 줄) — 메뉴가 아무리 늘어나도 로그아웃 버튼이 화면 밖으로 밀려나는 문제만은 항상 방지됨 | "길이 증가" 자체를 줄이는 게 아니라 "밀려나서 안 보이는" 최악의 상황만 막는 대책이라, 스크롤이 필요해지는 근본 문제는 남음 |
| 5. `설정`을 처음엔 3개 메뉴로만 유지하고, 진단류는 별도 대분류를 만들지 않음 | 이번 문서에서 실제로 채택한 방향. `진단 스냅샷`을 `설정`에서 빼서(§3.3) 증가분을 최소화 | 추가 컴포넌트/상태 관리 없이 지금 당장 적용 가능. `설정`이 "값을 바꾸는 메뉴들"로만 좁게 유지돼 §3.3에서 우려한 오해(조회 전용 진단을 설정으로 오인)도 함께 해결됨 | 근본적인 "메뉴가 계속 늘어나는 문제"는 미해결 — 이후 화면이 더 늘어나면 대안 1이나 4가 다시 필요해짐 |

### 4.3 1차 추천안

**이번 `설정` PR 단계에서는 대안 5(메뉴 수를 최소화)를 채택**한다 — `진단 스냅샷`을 `설정`에서
제외하고(§3.2, §3.3), `예약됨 > 관리`를 제거해 증가분을 상쇄한다. 순증가는 `설정` 그룹 헤더
1개 + 하위 메뉴 3개 = 4행이고, `예약됨 > 관리` 제거로 1행이 줄어 실제 순증가는 3행이다.

이 정도 증가는 지금 사이드바 구조(그룹 접기 없이도 동작해 온 기존 14행)에서 감내할 수 있는
수준으로 판단해, **대안 1(그룹 접기/펼치기)이나 대안 4(내부 스크롤)를 이번 PR에서 함께
구현하지는 않는다.** 다만 `설정` 하위에 §3.3의 진단 화면들이 실제로(다른 화면에 흡수되는 대신)
독립 메뉴로 늘어나거나, 다른 화면이 추가로 `설정`/`운영 모니터링`에 붙는 시점이 오면, 그때는
대안 1(그룹 접기/펼치기) 또는 대안 4(사이드바 내부 스크롤 + 로그아웃 버튼 고정)를 별도 작업으로
재검토해야 한다 — 특히 대안 4는 구현 비용이 매우 작아 대안 1보다 먼저 시도해 볼 만하다.

## 6. 추천 메뉴 분류

**바로 화면화 가능(백엔드 변경 없이 프론트만으로):**
- `execution.fee_tax` 조회 카드(`/active`, `/at`)
- `execution.fee_tax` dry-run 미리보기

**백엔드 선행 필요:**
- `whoami`/`/auth/me` 역할 조회 API
- `risk.max_single_position_pct` 현재값 조회 API
- 기타 리스크 한도(`daily_loss_limit_pct` 등) 발행 API — 범위 자체가 아직 정의되지 않음

**기존 화면에 붙이는 게 적절:**
- `PUT /orders/{id}/status` → `정합성 점검`(`ReconciliationView.tsx`) 화면의 행 단위 조치

**설정 메뉴가 아니라 후속 관측 화면 후보(§3.3):**
- `guardrail-evaluations` → `의사결정`/`주문내역` 상세의 차단 근거
- `risk-limit-snapshots` → `운영 경고`/`계좌`/`의사결정` 상세의 리스크 근거 카드
- `signal-feature-snapshots` → `의사결정` 상세의 신호 근거

   라우트 추가(각각 최소 placeholder 컴포넌트, 실제 데이터 연동은 다음 단계).
3. **`수수료·세금 정책` 조회 전용 화면** — `getActiveExecutionFeeTaxPolicy`/`getExecutionFeeTaxPolicyAt`
   client 함수 신설, §7.2의 "현재 활성 정책"/"특정 시점 조회" 섹션까지만 구현(발행 없음).
4. **`수수료·세금 정책` dry-run 미리보기** — 변경안 입력 폼 + `dry_run=true` 호출 + 결과 카드.
   이 단계까지는 아직 실제 값이 바뀌지 않으므로 리스크가 낮다.
5. **`수수료·세금 정책` 실제 발행 기능** — §7.5의 공용 `ConfirmModal` 신설 + `dry_run=false` 제출 +
   401/403/400/500 개별 처리(§2.4) + 성공 후 "현재 활성 정책" 재조회(optimistic update 금지).
6. **`risk.max_single_position_pct` 조회 API 추가 후 읽기 전용 카드** — 백엔드
   `GET /config-versions/risk/max-single-position-pct/active`류 신설(§5 표) → §7.3의 "준비 중"
   상태를 실제 조회 카드로 교체(이 시점까지는 발행 버튼 없이 조회만).
7. **`정합성 점검` 화면의 수동 상태 확정 조치** — §7.4. 3단계에서 만든 `ConfirmModal` 재사용.
   `role=viewer`면 버튼 자체를 숨기고(1단계 산출물 재사용), 제출 후 목록을 재조회해 해당 행이
   실제로 상태 전이됐는지 확인시켜준다(낙관적 업데이트 금지, 원칙 5).

각 단계는 앞 단계 산출물(role 상태, `ConfirmModal`, client 함수)을 재사용하도록 순서를 잡았고,
단계별로 독립적으로 검증/병합 가능하다. **`진단 스냅샷` 관련 메뉴 구현 단계는 이번 계획에
포함하지 않는다** — §3.3에서 정리한 "관측성 개선 후보"로만 남기고, 실제 구현은 각 대상 화면
(`DecisionsView`/`OrdersView`/`AccountsView`/`OperationsAlertsView`)의 별도 후속 설계에서 다룬다.

## 9. 1순위 추천 작업

**1단계(`whoami`/role API + 프론트 권한 상태 표시)를 최우선으로 추천한다.**

근거:
- 이 문서의 §7.1/§7.4/§8 3~5·7단계 전부가 "지금 이 토큰이 admin인지 viewer인지"를 프론트가 알고
  있다는 전제 위에 설계돼 있다. 이 전제가 없으면, viewer 권한으로 접속한 운영자가 "수정"/"발행"/
  "상태 확정" 버튼을 눌렀다가 이유를 알 수 없는 403만 받게 되어, `admin_ui/AGENTS.md`의
  "인증 실패와 권한 부족을 같은 메시지로 뭉개지 않는다" 원칙을 그대로 위반하는 화면이 나온다.
- 이번 조사로 확인한 사실 — 이 시스템의 인증은 **프로세스 시작 시 설정된 토큰 1개 + 고정 role
  1개**([`security.py:44-63`](../../src/agent_trading/api/security.py))라서, "사용자별 권한
  관리" 같은 복잡한 기능이 아니라 "지금 내가 쓰는 토큰의 role이 뭔지 보여주는 것"만으로 충분하다.
  구현 범위가 매우 작다(`GET /auth/me` 1개 + `AuthContext` 필드 1개 추가).
- 이 작업은 다른 어떤 쓰기 기능과도 의존관계가 없어 독립적으로 먼저 병합할 수 있고, 병합 즉시
  "지금 이 배포가 admin 토큰으로 떠 있는지"를 운영자가 화면에서 바로 확인할 수 있게 되어 그
  자체로도 즉시 가치가 있다(현재는 이걸 확인하려면 배포 설정 파일을 직접 봐야 함).

## 10. 미확인 사항

- **실제 admin 토큰 운영 정책**: 지금 운영 환경(`/etc/agent_trading/*.env` 등)에 실제로 admin
  role 토큰이 발급/배포돼 있는지, 아니면 지금까지 전부 viewer 토큰만 써 왔는지는 이번 조사에서
  확인하지 않았다(설정 파일 값을 직접 열람하지 않음 — secret 노출 금지 원칙).
- **설정 변경 승인 절차**: `POST` 발행 API에 `reason` 필드가 있어 "왜 바꿨는지"는 남길 수 있지만,
  "누가 승인했는지"를 화면에서 요구할지(예: 2인 승인) 여부는 운영 정책 결정 사항이라 이번 설계
  범위 밖으로 남긴다.
- **변경 이력과 audit log 연결**: `config_version_admin.py`가 `audit_logs`에 기록을 남기는 것으로
  보이나(`action="config_version.risk.max_single_position_pct.update"`), Admin UI에 이미 있는
  `getAuditLogs` client 함수(현재 화면에서 미사용)를 `설정` 화면의 "최근 발행 이력"에 필터링해서
  붙일 수 있는지는 `audit_logs` 스키마의 필터 파라미터를 더 살펴봐야 한다(§7.2의 "최근 발행 이력"을
  이번엔 "현재 활성 1건"으로만 좁혀 놓은 이유).
- **fee_tax 정책을 누가/언제 바꿀 수 있어야 하는지**: 이 정책이 실제 운영에서 얼마나 자주
  바뀌는 값인지(초기 1회 설정 후 거의 안 바뀌는 값인지, 주기적으로 조정하는 값인지)는 도메인
  지식이 필요해 확인하지 못했다 — 이력 목록 UI의 필요성(§10 위 항목)과도 연결된다.
- **리스크 한도 API 확장 범위**: `daily_loss_limit_pct`/`weekly_loss_limit_pct`/`max_drawdown_pct`/
  `kill_switch.*` 등을 `max_single_position_pct`와 같은 패턴(immutable append + 조회 API)으로
  확장할지, 아니면 이 값들은 애초에 자주 안 바뀌는 값이라 API화하지 않고 배포 설정으로 남길지는
  백엔드/리스크 정책 오너의 판단이 필요하다 — 이번 문서는 "화면 설계" 범위이므로 이 결정을
  선행하지 않는다.
- **§3.3의 후속 관측 화면 후보를 실제로 어느 화면에 흡수할지**: `risk-limit-snapshots`를
  `운영 경고`와 `계좌` 중 어디에 먼저 붙일지처럼, 표에 제시한 "제안 위치"는 1차 판단이고
  실제 구현 착수 시점에 해당 화면 설계에서 재검토가 필요하다.
- **좌측 내비 세로 길이 문제의 장기 해법**: §4.3에서 이번 PR은 메뉴 최소화로만 대응하기로 했으나,
  이후 화면이 더 늘어났을 때 대안 1(그룹 접기)과 대안 4(내부 스크롤) 중 어느 쪽을 먼저 적용할지,
  또는 둘 다 필요한지는 이번 문서에서 결정하지 않았다.

# 실현손익(Realized PnL) 화면 설계서

## 목적

이 문서는 Admin UI에 새로 추가할 **실현손익 조회 화면**의 배치, 레이아웃, 데이터 흐름, API 매핑을 정의한다.

계산 엔진/저장 계층/recompute 서비스/read-only Inspection API는 이미 구현되어 있다([`kis_realized_pnl_moving_average_action_plan.md`](../docs/40_action_plans/kis_realized_pnl_moving_average_action_plan.md) 4~5단계, [`12_realized_pnl_moving_average_ledger.md`](../docs/00_foundational_design/detailed_design/12_realized_pnl_moving_average_ledger.md)). 이 문서는 **화면 설계 단계**이며, 코드는 아직 작성하지 않는다.

## 요구사항 (사용자 지정)

1. 별도의 화면으로 만든다.
2. 위치는 왼쪽 내비게이션의 "계좌" 메뉴 하위(인덴트)에 "실현손익"으로 노출한다.
3. 전체 레이아웃은 증권사 HTS의 실현손익 화면과 비슷한 구조로 한다.
4. 기간별 실현손익을 조회할 수 있는 구조로 한다.

## 스펙 충돌 분석 (중요 — 반드시 먼저 읽을 것)

### 충돌 없음

- **화면 분리(요구 1)**: 기존 라우팅이 `orders` → `orders/:orderId` 같은 중첩 패턴을 이미 쓰고 있어 `accounts` → `accounts/realized-pnl`로 자연스럽게 확장된다. 백엔드/데이터 계층과 무관.
- **HTS 스타일 레이아웃(요구 3)**: 순수 UI 관심사. 백엔드 read-only API 계약과 충돌하지 않는다.

### 설계 결정이 필요함(충돌은 아님) — 내비게이션 인덴트(요구 2)

현재 `admin_ui/src/components/Layout.tsx`의 nav 구조(`NavSection` → `NavItem[]`)는 **완전히 flat**하다. 부모-자식 관계나 들여쓰기 개념 자체가 코드에 없다. 두 가지 구현 옵션이 있다.

| 옵션 | 방법 | 장단점 |
|---|---|---|
| A. 시각적 인덴트만 | "계좌" `NavItem` 바로 다음에 `실현손익` 항목을 추가하고 CSS `padding-left`만 더 준다 | 구현 최소, 타입 변경 없음. 다만 "계좌"가 활성 상태일 때 하위 항목이 같이 강조되는 등 진짜 트리 동작은 없다 |
| B. 진짜 트리 구조 | `NavItem`에 `children?: NavItem[]` 추가, "계좌" 항목 확장/축소(accordion) UI 구현 | 의미상 정확하지만 `Layout.tsx`의 렌더링 로직(`NavSectionsList`)을 다시 짜야 한다 |

**권장**: 1차 구현은 **옵션 A**로 진행한다. 이 화면 하나만 하위에 두는 상황에서 트리 컴포넌트를 새로 만드는 비용이 과하다. 하위 메뉴가 2개 이상으로 늘어나면 그때 옵션 B로 전환한다.

### 실질적인 API 갭 — 기간별 "계좌 전체" 집계(요구 4)

현재 read-only Inspection API([`realized_pnl.py`](../src/agent_trading/api/routes/realized_pnl.py)) 계약:

| Endpoint | `instrument_id` | 날짜 필터 | 범위 |
|---|---|---|---|
| `GET /performance/realized-pnl/positions` | 선택(생략 시 계좌 전체) | **없음** | all-time 누계만 |
| `GET /performance/realized-pnl/daily` | **필수** | `start_date`/`end_date` | 종목 1개 |
| `GET /performance/realized-pnl/events` | **필수** | `before`(단일 상한) | 종목 1개 |
| `GET /performance/realized-pnl/recompute-queue` | 선택 | 없음 | 큐 상태만 |

HTS 실현손익 화면의 전형적인 1차 화면 — "계좌 전체, 이번 달 실현손익 합계 + 종목별 손익 리스트" — 를 **단일 호출로 얻는 경로가 없다**. `positions`는 종목 필터 없이 계좌 전체를 주지만 날짜 필터가 없고(all-time), `daily`/`events`는 날짜 필터가 있지만 종목을 반드시 지정해야 한다.

**해결 방안 (이번 화면 설계에 반영)**:

- **1차(P0, 신규 백엔드 불필요)**: `positions`(`instrument_id` 생략)로 종목 후보 목록을 먼저 얻고, 선택된 기간에 대해 종목별로 `daily`를 개별 호출해 프런트에서 합산한다. N+1 호출이지만 이 저장소의 다른 read 경로(`positions.py`의 종목명 조회, recompute 서비스의 fill 수집)도 같은 N+1 패턴을 이미 쓰고 있어 새로운 패턴은 아니다. 계좌당 종목 수가 크지 않은 운영 콘솔이라는 전제에서 실무적으로 감당 가능하다고 판단한다.
- ~~**후속(P1, 백엔드 확장 후보)**: 계좌×기간 단위로 `realized_pnl_daily_aggregates`를 종목 구분 없이 합산해 반환하는 신규 read-only endpoint~~ → **구현 완료.** `GET /performance/realized-pnl/summary?account_id=&start_date=&end_date=[&instrument_id=]`(`src/agent_trading/api/routes/realized_pnl.py`). `RealizedPnlDailyAggregateRepository.list_by_account()`를 최소 추가해 종목별 `daily` 반복 호출 없이 단일 조회로 계좌 전체 종목의 일자 집계를 가져온다. **Admin UI 전환 완료.** `RealizedPnlView.tsx`가 요약 카드/종목별 탭(+recompute 배지)을 이 endpoint 단일 호출로 채운다(계좌 전체·단일 종목 공통 경로). 종목 "전체"의 종목별 `daily` N+1은 이 두 화면 요소에서는 제거됐다.

탭 A(일자별)의 남은 N+1은 별도 endpoint `GET /performance/realized-pnl/daily-summary?account_id=&start_date=&end_date=`로 **백엔드 구현 완료**했다(`summary`와 계약을 공유하지 않는 추가 endpoint — `summary`는 종목별 groupby, `daily-summary`는 날짜별 groupby로 역할이 분리돼 있다). 신규 repository 메서드는 필요 없었다 — `summary`가 이미 쓰는 `RealizedPnlDailyAggregateRepository.list_by_account()`를 그대로 재사용한다. **Admin UI 탭 A의 전환은 아직 미착수**(후속) — 현재 탭 A는 여전히 종목별 `daily` 반복 호출 후 프런트에서 날짜별 합산하는 기존 경로를 쓴다.
- 사용자가 특정 종목을 선택한 뒤의 상세 조회(체결별 실현손익)는 이미 `events`가 정확히 그 형태(종목 1개 + 기간 필터)를 지원하므로 갭이 없다.

### 종목 후보 목록에 "전체매도로 포지션이 0인 종목"이 빠지지 않는가 (확인 완료)

`positions`(`PositionCostBasisStateRepository.list_by_account()`)가 반환하는 종목 후보 목록은 **현재 보유 수량(`quantity`)으로 필터링하지 않는다**. 코드로 직접 확인한 근거는 다음과 같다.

- `position_cost_basis_state` 행은 그 계좌×종목에 첫 fill이 적용된 순간 생성되고, 이후 어떤 경로도 이 행을 **삭제하지 않는다** — `RealizedPnlLedgerService.apply_fill()`(실시간 반영)과 `RealizedPnlRecomputeService`(replay 복구) 둘 다 결과 수량이 얼마이든(0 포함) 항상 `upsert()`만 호출한다(`realized_pnl_ledger_service.py`, `realized_pnl_recompute_service.py` 확인).
- `list_by_account()`의 실제 조회 조건은 `account_id` 일치뿐이다(`memory.py`/`postgres/position_cost_basis_states.py` 둘 다 `quantity` 조건 없음).
- 따라서 전체매도로 `quantity == 0`이 된 종목도 이 목록에서 **빠지지 않는다** — 종목 후보 열거 단계에서는 문제가 없다.

**다만 구현 시 반드시 지킬 주의사항(리스크는 여기 있음)**: 이 화면의 "종목 후보 목록"과 별개로, 다른 화면(예: 기존 `AccountsView`의 포지션 테이블)이나 UI 컴포넌트를 재사용할 때 "보유 중인 종목만 보여준다"는 의도로 `quantity > 0` 필터를 관례적으로 걸어둔 경우가 있을 수 있다. 이 실현손익 화면의 종목 후보 열거 로직에는 **그런 필터를 절대 추가하지 않는다** — "보유 종목" 개념과 "실현손익 조회 후보 종목" 개념은 다르며, 후자는 과거에 활동이 있었던 모든 종목(현재 미보유 포함)을 포함해야 한다. 구현 단계에서 이 부분에 대한 단위 테스트(quantity=0인 `position_cost_basis_state`가 후보 목록에 포함되는지)를 반드시 추가한다.

## 배치 / 내비게이션

- 1단계: `계좌` (기존, `to: "/accounts"`)
- 2단계(신규, 인덴트): `실현손익` (`to: "/accounts/realized-pnl"`)
- 라우트: `App.tsx`의 `<Route path="accounts" element={<AccountsView />} />` 옆에 `<Route path="accounts/realized-pnl" element={<RealizedPnlView />} />` 추가(기존 `orders/:orderId` 패턴과 동일).
- 아이콘: **독립된 주제 아이콘(예: `TrendingUp`/`PieChart`)을 쓰지 않는다.** "계좌"의 하위 항목임이 한눈에 인식되도록, 하위 관계를 나타내는 기호형 아이콘을 쓴다 — `lucide-react`의 `CornerDownRight`(꺾인 화살표, "이 항목에서 파생됨"을 표현) 또는 더 단순하게 작은 인덴트 점/선(`•`, `└`)을 아이콘 자리에 배치하는 방식을 검토한다. 최종 선택은 실제 구현 시 디자인 검토를 거친다.

## 화면 구조 (HTS 실현손익 화면 참조)

전형적인 국내 HTS 실현손익 화면은 상단 조회 조건(계좌/기간/종목) + 요약 영역(총계) + 하단 상세 테이블(종목별 또는 체결별) 구조를 쓴다. 이 화면도 동일한 구조를 따른다.

### 1. 조회 조건 바 — 계좌/기간/종목을 한 프레임의 한 행에 배치 (타이틀 바로 아래, sticky)

**계좌 선택을 별도 영역으로 분리하지 않고, 기간·종목 선택과 같은 행에 한 프레임으로 묶는다.** (이전 초안에서 "0. 계좌 선택 영역"으로 분리했던 것을 통합)

- **계좌**: 단일 계좌 선택 컴포넌트(드롭다운 또는 검색 가능한 선택 UI, 기존 `AccountsView`의 계좌 검색/필터 UX 재사용). **"전체 계좌"(계좌 간 합산/비교) 옵션은 제공하지 않는다** — 항상 정확히 하나의 계좌만 선택된 상태로 동작한다. 이 제약은 백엔드 계약과 정확히 일치한다: `positions`/`daily`/`events`/`recompute-queue` 4개 endpoint 모두 `account_id`가 필수 파라미터이고 여러 계좌를 한 번에 조회하는 경로 자체가 없다(종목 차원과 달리 이 축에는 API 갭이 없다).
- **기간 — 항상 날짜 범위(기간)를 기본으로 한다.** 프리셋 버튼(`오늘` / `1주` / `1개월` / `3개월` / `올해`) + 직접 날짜 범위 입력(`start_date`/`end_date`). API에는 항상 `start_date`/`end_date` 두 값을 함께 전달한다.
  - **"특정일자만" 단일 선택 모드는 별도 1급 컨트롤로 두지 않는다.** 당초 "PK가 `(account_id, instrument_id, trade_date)`라 하루 단위 조회 자체는 기술적으로 문제 없다"고 검토했지만, 이미 전체매도로 종목이 종료된 경우 "그게 정확히 며칠이었는지"를 사용자가 미리 알고 있어야 특정일자 모드로 찾을 수 있다는 실사용 관점 문제가 있다 — 기간(범위) 조회는 그 날짜가 범위 안에 포함되기만 하면 되므로 이 문제가 없다. 따라서 **기간을 1차 상호작용으로 유지**하고, "하루만 보고 싶다"는 요구는 날짜 범위 피커에서 시작일=종료일로 직접 지정하는 것으로 충분히 커버한다(별도 모드 전환 UI를 추가하지 않는다).
- **종목**: `전체`(기본) 또는 특정 종목. `전체` 선택 시 위 "API 갭" 절의 1차 해결 방안(N+1 합산)이 적용된다. 특정 종목 선택 시 `daily`/`events`를 그 종목으로 바로 호출한다.
- **조회** 버튼: 같은 행 맨 끝에 둔다. 계좌/기간/종목 중 무엇을 바꾸든 이 버튼을 눌러야 반영된다(이전 초안의 "계좌는 즉시 반영" 규칙은 통합하면서 제거 — 한 프레임 안의 조건들은 모두 같은 트리거를 공유하는 것이 자연스럽다). 단, 계좌를 아직 선택하지 않은 초기 상태는 에러가 아니라 안내 상태로 표시한다 — "조회할 계좌를 선택하세요"와 함께 아래 요약/테이블 영역은 비활성 또는 숨김 처리, `조회` 버튼도 비활성화한다.

### 2. 요약 영역 (조회 조건 바로 아래, 작은 카드 4개 — 확정)

**카드 4개를 한 줄로 나열하되, 카드 안 내용은 라벨과 값을 세로 2줄이 아니라 "라벨 : 값" 1줄로 표시**해 카드의 세로 폭을 줄인다(예: 카드 안에 `매도 건수 : 18건` 한 줄만). 선택한 계좌×기간×종목(또는 전체) 기준 합계 4가지를 각각 별도 카드로 노출한다.

- 카드 1: `실현손익 합계 : +1,234,500원`(순, `realized_pnl_net`/`realized_pnl_net_sum` 합산)
- 카드 2: `매도 건수 : 18건`(`sell_event_count` 합산 또는 event 건수)
- 카드 3: `매도금액 합계 : 22,400,000원`
- 카드 4: `비용 합계 : 33,600원`(수수료+세금 합산 — 아래 탭의 "비용" 컬럼과 동일 정의)

**중요 — 이 4개 확정으로 authoritative source가 바뀐다.** `realized_pnl_daily_aggregates`는 `realized_pnl_net_sum`/`sell_event_count`만 저장하고 매도금액/매수금액/비용은 **저장하지 않는다**. 이 값들은 `realized_pnl_events`의 `sell_quantity`/`sell_price`/`avg_cost_basis_before`/`fee`/`tax`를 이벤트 단위로 합산해야만 얻을 수 있다 — 자세한 내용과 해결 방안은 아래 "신규 API 갭 — 매도금액/매수금액/비용은 저장되지 않는다" 절 참고.

`recompute_required=true`인 종목이 이 기간에 포함돼 있으면 같은 줄 또는 바로 아래에 경고 배지(`재계산 대기중 — N개 종목`)를 노출한다 — `positions` endpoint의 `recompute_required`/`recompute_reason`을 그대로 쓴다. HTS와 달리 이 시스템은 이동평균 재계산이 비동기로 일어날 수 있으므로, "이 수치가 아직 확정이 아닐 수 있다"는 신호를 반드시 표시해야 한다(`admin_ui/AGENTS.md`의 "위험하거나 불확실한 상태는 정상처럼 표시하지 않는다" 원칙).

### 3. 상세 테이블 (탭 구조)

세 개 탭으로 구성한다 — HTS의 "일별" / "종목별" / "체결별" 탭 구조와 동일.

#### 탭 A — 일자별

**컬럼 순서(확정): 날짜, 매도 건수, 매수금액, 매도금액, 비용, 실현손익(순).** `비용 = 수수료 + 세금`.

- 종목 `전체` 선택 시: 날짜별로 여러 종목의 이벤트를 합산한 행.
- 특정 종목 선택 시: 그 종목의 이벤트를 날짜별로 합산한 행.
- `날짜`/`매도 건수`/`실현손익(순)`은 `daily` aggregate로 바로 얻을 수 있지만, `매수금액`/`매도금액`/`비용`은 `daily`에 없는 필드라 `events`를 날짜별로 그룹핑해 합산해야 한다(아래 API 갭 절 참고) — 결과적으로 이 탭은 `daily`가 아니라 **`events` 전량이 authoritative source**가 된다.
- 정렬: 날짜 오름차순(API 기본값과 동일) 또는 최신순 토글.

#### 탭 B — 종목별 (종목 `전체`일 때만 노출)

**컬럼 순서(확정): 심볼, 종목, 매도 건수, 매수금액, 매도금액, 비용, 실현손익(순), 상태.**

- `positions` 목록(선택 기간에 활동이 있었던 종목만 필터링 — 필터링 자체는 프런트에서 탭 A 집계 결과 기준으로 수행)에서 심볼/종목명을 가져오고, 나머지 수치(매도 건수/매수금액/매도금액/비용/실현손익)는 탭 A와 동일하게 그 종목의 `events`를 합산해 채운다.
- `상태` 컬럼 = `recompute_required` 배지(해당 종목이 재계산 대기 중이면 표시, 아니면 빈 칸).
- 행 클릭 → 종목 선택 상태로 전환 + 탭 C(체결별)로 드릴다운.

#### 탭 C — 체결별 (종목 선택 시에만 노출)

**컬럼 순서(확정): 체결시각, 수량, 매수단가, 매도단가, 비용, 실현손익(순).**

- `수량` = `sell_quantity`, `매도단가` = `sell_price`, `비용` = `fee + tax`, `실현손익(순)` = `realized_pnl_net` — 전부 `events`에 그대로 있는 필드다.
- **`매수단가`는 `avg_cost_basis_before`를 그대로 쓴다.** 이동평균법에서는 "매도 직전 평균단가"가 곧 그 시점의 실질적인 매수 평균단가이므로 별도 필드가 필요 없다 — 요청하신 "매도전평균이 매수평균단가와 같다면 매도전평균은 매수단가로 표시"는 이 시스템에서는 항상 참이다(이동평균법 자체가 매도 시점에 "매수단가=그 시점 평균단가"를 쓰는 방식이라, `avg_cost_basis_before`가 다른 값이 되는 경우가 없다). 그래서 컬럼 라벨을 처음부터 "매수단가"로 쓰고 내부 값은 `avg_cost_basis_before`를 그대로 매핑한다 — 조건 분기나 별도 계산이 필요 없다.
- `fee_tax_source`/`realized_pnl_gross`/`position_quantity_after`는 이 탭의 기본 컬럼에는 넣지 않는다(필요하면 행 확장/툴팁으로 보조 노출 검토 — 이번 설계서 범위에서는 미확정).
- `limit`/`before` 기반 페이지네이션(1차는 "더 보기" 버튼, 위 결정 참고).

## 신규 API 갭 — 매도금액/매수금액/비용은 저장되지 않는다 (중요)

컬럼 확정 과정에서 새로 발견된 갭이다. 정리하면:

| 필요한 값 | 저장 여부 | 얻는 방법 |
|---|---|---|
| 실현손익(순) 합계 | `realized_pnl_daily_aggregates.realized_pnl_net_sum`에 **저장됨** | `daily` 호출로 바로 획득 |
| 매도 건수 | `realized_pnl_daily_aggregates.sell_event_count`에 **저장됨** | `daily` 호출로 바로 획득 |
| 매도금액 | **저장 안 됨** | `realized_pnl_events`의 `sell_quantity × sell_price`를 이벤트마다 계산해 합산 |
| 매수금액 | **저장 안 됨** | `realized_pnl_events`의 `sell_quantity × avg_cost_basis_before`를 이벤트마다 계산해 합산 |
| 비용(수수료+세금) | **저장 안 됨** | `realized_pnl_events`의 `fee + tax`를 이벤트마다 계산해 합산 |

즉 탭 A(일자별)와 탭 B(종목별)에 매수금액/매도금액/비용을 넣기로 확정하면서, 이 두 탭은 더 이상 가벼운 `daily` 호출만으로 완성되지 않고 **해당 기간의 `events` 전량을 페이지네이션으로 끝까지 가져와야** 한다(1페이지 `limit`만으로는 부족 — 날짜별/종목별 합산이 누락될 수 있다). 이건 이 화면 전체의 비용 구조를 바꾸는 변화라 명확히 표시한다.

- **종목을 특정 종목 하나로 좁힌 상태**: 그 종목의 `events`를 기간 전체에 대해 페이지네이션으로 모두 가져와 날짜별로 그룹핑 — 상대적으로 감당 가능하다.
- **종목 `전체` 상태**: 이미 있던 "종목별 N+1" 문제에, 이제는 "종목마다 `daily` 1번 호출"이 아니라 "종목마다 `events` 전량 페이지네이션"으로 바뀐다 — 종목 수 × 종목당 이벤트 페이지 수만큼 호출이 늘어난다. 활동이 많은 계좌에서는 체감 로딩 시간이 크게 늘어날 수 있다.

**해결 방안**:

- **1차(임시, 신규 백엔드 불필요)**: 위 방식대로 프런트에서 `events` 전량을 가져와 합산한다. `sell_quantity × sell_price`/`sell_quantity × avg_cost_basis_before`/`fee + tax`는 전부 단순 산술(가격 곱셈/덧셈)이라 이동평균/실현손익 계산 로직을 복제하는 것이 아니다 — 원가 결정이나 이동평균 갱신 같은 도메인 계산은 여전히 백엔드에만 있다. **다만 이 방식은 "종목 하나로 좁힌, 드문 경우"를 위한 임시 완화책이 아니라는 점을 분명히 한다** — 아래 재평가 참고.
- **재평가: 백엔드 확장(`daily` aggregate에 매수금액/매도금액/비용 합계 컬럼 추가)을 P1(후속)이 아니라 이 화면의 선행/동시 작업으로 올린다.** 이유: 종목 선택의 **기본값이 "전체"**다(위 조회 조건 바 정의) — 즉 사용자가 특정 종목으로 좁히는 것은 선택적 행동이고, "전체" 상태로 화면을 여는 것이 기본 동작이다. 그러므로 "종목 전체일 때만 무겁다"는 이전 판단은 "가끔 발생하는 무거운 경로"가 아니라 **매번 화면을 열 때마다 발생하는 기본 경로**를 가리키는 것이었다 — 운영 데이터로 종목 수를 확인해 우선순위를 정하겠다는 이전 계획(열린 이슈 3번)은 전제 자체가 틀렸다. 종목 수가 적더라도 매 방문마다 "종목 수 × `events` 전량 페이지네이션"이 발생하므로, 신규 migration + 계산 엔진 수정(`RealizedPnlLedgerService`의 실시간 갱신 경로, `RealizedPnlRecomputeService._rebuild_daily_aggregates`에 `buy_amount_sum`/`sell_amount_sum`/`fee_tax_sum` 합계를 함께 쓰도록 추가)을 **이 화면의 프런트 구현과 병행하거나 그보다 먼저 진행하는 것을 권장**한다. 백엔드 확장이 아직 없는 상태로 화면을 먼저 배포해야 한다면, 최소한 "전체" 조회에 로딩 상태/예상 소요 시간을 명확히 표시해 운영자가 무거운 조회임을 인지하게 해야 한다.

이 화면은 **read-only이며 도메인 계산을 하지 않는다** — 프런트에서 하는 산술은 (1) `daily`/`events` 여러 호출 결과의 단순 합산, (2) `events` 필드 간 단순 곱셈/덧셈(매도금액=수량×가격, 비용=수수료+세금)뿐이다. 이동평균 원가 갱신, 실현손익 자체의 산출식은 절대 프런트에 복제하지 않는다 — 그 값(`realized_pnl_gross`/`realized_pnl_net`/`avg_cost_basis_before`)은 항상 백엔드가 계산해 저장한 값을 그대로 읽는다.

## 상태 표현 규칙

- **로딩**: 조회 조건 바 아래 skeleton, 이전 조회 결과는 유지하지 않고 명확히 초기화(오해 방지).
- **빈 상태**: 선택한 계좌×기간에 실현손익 활동이 없으면 "이 기간 동안 실현손익이 없습니다" — 에러가 아님을 명확히 한다(`accept backend-file` 테스트에서도 빈 목록은 200/정상 응답으로 이미 검증됨).
- **에러**: API 오류(4xx/5xx)는 빈 목록으로 숨기지 않고 별도 에러 배너로 표시(`admin_ui/AGENTS.md` 금지 사항 준수).
- **재계산 대기(`recompute_required=true`)**: 정상 색상(녹색/파란색 계열)로 표시하지 않는다. 주의 색상(주황/노랑 계열) + "이 종목의 실현손익 값은 재계산 대기 중이라 변경될 수 있습니다" 툴팁.
- **freshness**: `positions`의 `updated_at`을 화면 어딘가(요약 영역 또는 종목별 테이블 각 행)에 노출해 "이 값이 언제 마지막으로 갱신됐는지"를 운영자가 판단할 수 있게 한다.

## 반응형 / 데스크톱 우선

- `admin_ui/AGENTS.md`와 기존 `near_real_ops_monitoring_ui_spec.md` 원칙과 동일하게 desktop-first, 고밀도 테이블 우선.
- 모바일에서는 탭 구조를 유지하되 조회 조건 바를 접이식으로 축소.

## API 매핑 요약

### 기존 API로 바로 가능

- 조회 조건 바, 요약 영역(종목 선택 시), 탭 A(종목 선택 시), 탭 B, 탭 C — 모두 기존 4개 realized-pnl endpoint + 계좌 목록(`GET /accounts`)으로 충분.

### 프런트 워크어라운드가 필요

- 요약 영역 + 탭 A의 "종목 전체" 합계 — `positions`로 종목 열거 후 종목별 `daily` N+1 호출 + 프런트 합산(위 "API 갭" 절 참고).

### 후속 백엔드 확장 후보(이번 설계서 범위 밖, 별도 승인 필요)

- `GET /performance/realized-pnl/summary?account_id=&start_date=&end_date=` — 계좌 전체·기간 단위 합계를 단일 호출로 반환(N+1 제거). 종목 수가 많은 계좌가 실제로 생기면 우선순위를 올린다.
- 기간 내 매도금액/수수료/세금 총계 — 현재는 `events`를 전량 훑어야 얻을 수 있어, 필요성이 확인되면 `daily` aggregate 자체에 필드를 늘리는 방안을 검토(신규 migration 필요 여부는 그때 판단).

- ~~`realized_pnl_daily_aggregates`에 매수금액/매도금액/비용 합계 컬럼 추가(신규 migration) + 계산 엔진 반영~~ → 완료. `db/migrations/0055_add_realized_pnl_daily_aggregate_amount_sums.sql`로 `buy_amount_sum`/`sell_amount_sum`/`fee_tax_sum` 3개 컬럼을 추가했고, `RealizedPnlLedgerService._update_daily_aggregate()`(실시간 증분)와 `RealizedPnlRecomputeService._rebuild_daily_aggregates()`(절대값 재구성) 양쪽에서 채운다. `GET /performance/realized-pnl/daily` 응답에도 그대로 노출된다. 상세 근거는 [`12_realized_pnl_moving_average_ledger.md`](../docs/00_foundational_design/detailed_design/12_realized_pnl_moving_average_ledger.md) 4.3절과 [`kis_realized_pnl_moving_average_action_plan.md`](../docs/40_action_plans/kis_realized_pnl_moving_average_action_plan.md)의 "5b단계" 참고.

### "더 보기" 버튼과 초기 로딩 시간

"더 보기" 버튼으로 하면 화면이 처음 뜨는 시각(초기 로딩)이 줄어드는지 확인한 결과: **"더 보기" 버튼 자체가 초기 로딩 시간을 줄여주는 요인은 아니다.** 초기 로딩 시간은 **첫 페이지에서 몇 건을 가져오는가**(`events` endpoint의 `limit`, 기본 200/최대 1000)로 결정되고, 이건 "더 보기" 버튼과 무한 스크롤 둘 다 첫 로딩 시점에는 동일하게 딱 그 `limit`만큼만 가져온다 — 두 방식 모두 페이지네이션 자체를 안 하고 전체 히스토리를 한 번에 불러오는 것보다는 초기 로딩이 빠르지만, "더 보기 vs 무한 스크롤" 사이에는 초기 로딩 시간 차이가 없다.

"더 보기" 버튼이 실제로 주는 이점은 초기 로딩이 아니라 다음 두 가지다.

- **불필요한 후속 요청을 만들지 않는다** — 무한 스크롤은 사용자가 스크롤만 내려도 2페이지, 3페이지 요청이 계속 발사된다. "더 보기"는 사용자가 명시적으로 누르지 않으면 추가 요청이 전혀 일어나지 않는다 — 대부분의 조회가 1페이지 안에서 끝나는 운영 콘솔 성격상(체결이 아주 많은 계좌×종목이 아니면) 총 API 호출 수를 줄이는 효과가 크다.
- **요청 타이밍이 예측 가능하다** — 짧은 시간에 스크롤을 연속으로 내려도 여러 요청이 겹쳐 발사되지 않는다.

이 화면(및 admin_ui 전체)에는 아직 페이지네이션 UI 선례가 없어(코드 검색 결과 "더 보기"/무한 스크롤 패턴 모두 미사용) 이번이 첫 도입이다. 위 이유로 **"더 보기" 버튼으로 예약**하고, `events` 호출의 `limit` 기본값(200)은 그대로 유지한다(필요시 조정 가능하지만 이번 설계서 범위에서 변경하지 않음).
